# Lush Guesser: проверочный этап Next.js (6 часов)

Цель этапа — проверить архитектуру полной замены Vite frontend на Next.js с Node runtime и получить личную практику. Это не срок выпуска в production. Основной код пишет кандидат без coding agent; после попытки агент помогает с review, отладкой и проверками.

## Исходное состояние

- Работать в отдельном worktree от актуального `dev`, сохранив все существующие изменения в основной рабочей копии и не подмешивая их в миграцию.
- До изменений записать результат `npm run lint --prefix frontend`, `npm run build --prefix frontend`, `npm run test:e2e` и текущий commit. Не исправлять посторонние ошибки в рамках перехода.
- Опираться на [официальное руководство миграции с Vite](https://nextjs.org/docs/app/guides/migrating/from-vite) и [Server/Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).

## Последовательность

| Время | Задача | Признак результата |
| --- | --- | --- |
| 0–60 мин | Изолировать работу, проверить baseline и выписать контракт игры, таблицы лидеров и Telegram загрузки | Текущий commit, результаты команд и список публичных путей записаны |
| 60–120 мин | Поднять Next.js App Router с Node runtime в `frontend`, перенести глобальные стили, шрифты и metadata | Стартовая страница собирается и открывается локально |
| 120–210 мин | Перенести интерактивную игру в Client Component, сохранить `i18next`, ресурсы и вызов Telegram `WebApp.ready()` | Игра запускается в браузере и проходит хотя бы один раунд |
| 210–285 мин | Проверить серверную страницу таблицы лидеров и обращение к существующему NestJS API; актуальные данные не должны застывать после сборки | В HTML/ответе страницы видны данные API; ошибка показана отдельно от пустой таблицы |
| 285–360 мин | Обновить локальную конфигурацию Playwright с Vite на Next.js, запустить сборку и один сквозной сценарий; записать оставшиеся задачи | Есть фактический результат проверок и оценка следующего этапа |

Если задача заняла больше отведённого времени, записать состояние и перейти к следующему решению без маскировки недоделок. Сначала доказать клиентскую игру и серверную загрузку данных; контейнеры и production меняются в следующем этапе.

## Вопросы для самостоятельного объяснения

1. Почему игра — Client Component, а чтение таблицы лидеров может жить в Server Component?
2. Где живёт адрес NestJS API для серверного запроса, а где публичный `/api` для браузера?
3. Как сделать таблицу лидеров актуальной после отправки нового результата и избежать устаревшего кеша?
4. Когда вызывается `Telegram.WebApp.ready()` и что происходит при обычном открытии сайта без Telegram?
5. Чем Node runtime здесь отличается от `output: 'export'` по возможностям и сопровождению?

## Критерий продолжения после 6 часов

Продолжать полную замену, если есть работающий Next.js build и понятен путь к сохранению игрового сценария, динамической таблицы лидеров, `/api/*` и `/webhook`. В противном случае зафиксировать конкретные блокеры, нужное время и выбрать, что убрать из объёма следующего этапа. Ежедневный час на поиск работы сохраняется в обоих случаях.

## Проверка полной замены после следующего этапа

- Caddy продолжает принимать host Nginx через прежний Unix socket; `/api/*` и `/webhook` идут в NestJS, страницы — в Next.js Node runtime.
- В браузере и Telegram Mini App работают начало игры, 10 раундов, завершение, отправка результата и актуальная таблица лидеров.
- Проверены обе локали, статические изображения/шрифты, состояния ошибки API и мобильный экран.
- Обновлены `playwright.config.ts`, Docker/Compose, CI и README; проверены lint, catalog checks, build, backend tests, e2e, Docker build и dev deployment.
- Production promotion проходит существующий путь feature → dev → main после проверки dev; факт успешного production деплоя фиксируется только после реальной проверки.
