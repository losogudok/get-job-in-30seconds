## 1. Стратегическое решение

### Основное позиционирование

1. **Senior Backend Engineer — Node.js / TypeScript / PostgreSQL / integrations / AI tooling.**
2. **Senior Fullstack Engineer — Node.js / TypeScript / React, backend 65–75%.**

### Дополнительные направления

3. **Senior Frontend React/TypeScript** — только вакансии, где ценятся архитектура, Node.js/BFF, AI-интерфейсы, SSE/WebSocket и техническое лидерство.
4. **Hands-on Team Lead / Tech Lead** — как stretch-направление, а не основной поток: недавний подтверждаемый опыт руководства командой в резюме слабее инженерного опыта.

**Контрольная точка после диагностики:** Senior Backend — целевое, но пока не доказанное позиционирование. Если проверки Node.js/PostgreSQL/distributed systems дают Red, немедленно изменить основной поток на **Senior Fullstack с сильным frontend** или **Senior Frontend**, где исторический senior-опыт убедительнее. Не маскировать Middle+/Senior Fullstack под Senior Backend только названием резюме.

Не распыляться на Python-first, C++, Java/Go и чисто менеджерские роли. За один месяц выгоднее продавать наиболее доказуемую специализацию: TypeScript/Node.js + интеграции + production + AI-assisted development.

## 3. Критические риски и пробелы

Здесь «пробел» означает либо слабое знание, либо отсутствие убедительного доказательства в резюме/GitHub. Первые два дня должны отличить одно от другого.

### P0 — устранить в первую неделю

#### 3.1. Достоверность карьерной истории

Пользователь сообщил, что не работал на полноценной работе с 2020 года, но [[Резюме]] показывает «Фармментал Групп, март 2022 — август 2025» как обычное место работы и самозанятость с 2025 года. На интервью это создаст риск провала background check и вопросов о формате, загрузке, команде и руководителе.

Действия:

- выписать правдивый формат каждого периода после 2020 года: штат / договор / part-time / проект / собственный продукт;
- не представлять проектную занятость как штатную;
- для каждого периода подготовить проверяемые факты: продукт, роль, команда, личный вклад, архитектурное решение, инцидент, результат;
- удалить или смягчить метрики, источник которых нельзя объяснить за 30 секунд;
- подготовить честный ответ на вопрос «почему не было полноценной работы и почему возвращаетесь сейчас» без оправданий и негативных деталей.

#### 3.2. Публичное портфолио сейчас снижает senior-сигнал

Проверено через открытый браузер/CDP:

- `remnawave-shop-bot`: всего 2 коммита, README остался стандартным текстом NestJS starter;
- `file-manager`: 1 коммит, README шаблона Next.js, в дереве публичного репозитория виден `.env`;
- `lush-guesser`: 3 коммита, GitHub показывает текст лицензии вместо описания продукта;
- на профиле заявлены масштабируемость и production-проекты, но публичные pinned-репозитории почти не показывают архитектуру, тесты, CI/CD, эксплуатацию и технические решения.

Действия до конца дня 5:

- немедленно проверить `.env` в `file-manager`: если там когда-либо были секреты — отозвать/сменить их; убрать файл из текущего дерева и истории;
- снять с pin слабые шаблонные репозитории либо привести их в презентабельный вид;
- переписать README одного основного проекта: задача, архитектура, схема, запуск одной командой, тесты, компромиссы, наблюдаемость, нагрузочные результаты;
- сделать осмысленную историю из 10–20 небольших коммитов вместо одного «initial commit»;
- добавить CI, тесты и техническое описание.

#### 3.3. Глубина Node.js / TypeScript не доказана

Нужно подтвердить без AI-подсказок:

- event loop, microtasks/macrotasks, libuv/thread pool;
- streams и backpressure;
- обработка ошибок, graceful shutdown, cancellation, memory leaks;
- worker_threads/child_process и границы применимости;
- TypeScript generics, narrowing, conditional/mapped types, decorators, variance и проектирование типов публичного API;
- NestJS DI, scopes, guards, interceptors, pipes, middleware, lifecycle.

#### 3.4. PostgreSQL и согласованность данных

Вакансии требуют больше, чем «работал с PostgreSQL»:

- `EXPLAIN (ANALYZE, BUFFERS)`, индексы и selectivity;
- транзакции, isolation levels, locks/deadlocks;
- миграции без простоя и параллельная работа старой/новой схемы;
- оконные функции, партиционирование;
- идемпотентность, outbox/inbox, reconciliation jobs.

#### 3.5. Распределённые системы и брокеры

В резюме заявлены надёжность и идемпотентность, но нет явного доказательства реальных Kafka/RabbitMQ/NATS-сценариев. Нужны:

- delivery semantics, consumer acknowledgements;
- retry/backoff, DLQ, poison messages;
- ordering, deduplication, idempotent consumer;
- eventual consistency, saga/compensation;
- circuit breaker, timeout, bulkhead, rate limiting, backpressure.

#### 3.6. Тестирование и production readiness

Нужно уметь показать и объяснить:

- unit, integration и e2e-тесты, test pyramid и contract testing;
- Dockerfile/Compose, CI pipeline;
- Kubernetes на уровне разработчика: Deployment, Service, ConfigMap/Secret, Job/CronJob, probes, resources, rollout;
- structured logs, metrics, traces, alerting, SLI/SLO;
- расследование инцидента и post-mortem.

## 4. Диагностика за первые два дня

Каждый блок выполнять без coding agent. После завершения можно использовать AI только для разбора ошибок.

### День 1

1. **JavaScript/Node.js — 90 минут:** 20 устных вопросов + 2 задачи на event loop, streams/backpressure и graceful shutdown.
2. **TypeScript — 60 минут:** реализовать типизированный event bus или API client с generics, discriminated unions и conditional/mapped types.
3. **PostgreSQL — 90 минут:** схема orders/payments; запрос с `EXPLAIN ANALYZE`; подобрать индекс; показать race condition и исправить транзакцией/lock.
4. **Карьерная история — 90 минут:** составить правдивую временную шкалу 2020–2026 и 8 историй STAR.

### День 2

1. **System design — 90 минут:** спроектировать обработку платежа/заказа при дублях, таймаутах провайдера и повторной доставке событий.
2. **Backend live coding — 90 минут:** NestJS endpoint с idempotency key, PostgreSQL и интеграционным тестом.
3. **React — 90 минут:** streaming UI на SSE с reconnect/cancel/error states и тестом.
4. **Leadership — 60 минут:** записать видеоответы на 6 ситуационных вопросов.

### Оценка

- **Green:** решение самостоятельно, объяснены альтернативы и отказоустойчивость.
- **Yellow:** решение работает, но требуется подсказка или нет объяснения trade-offs.
- **Red:** нет рабочего решения либо используются только общие слова.

Все Red становятся темами первой недели. Yellow — второй. Green только повторяются перед интервью.

## 5. Доказательный проект

### Название

`reliable-payments-orchestrator` — production-style сервис оркестрации платежей. Это не очередной CRUD: один компактный бизнес-процесс должен доказать работу с транзакциями, повторной доставкой, сбоями и эксплуатацией.

### Минимальный scope

- NestJS + TypeScript, PostgreSQL, Redis + BullMQ;
- `POST /payments` с `Idempotency-Key`;
- transactional outbox и worker;
- эмулятор внешнего платёжного провайдера;
- webhook inbox/deduplication;
- retry с exponential backoff и DLQ;
- небольшая React-панель: состояния операций и retry DLQ;
- structured logs, Prometheus/Grafana, OpenTelemetry trace/correlation ID;
- unit + integration + e2e и `k6`-сценарий;
- Docker Compose, GitHub Actions и реально проверенный запуск в `k3d`/`kind`;
- три ADR: outbox, гарантии доставки/идемпотентность, retries/DLQ;
- runbook «растёт очередь / недоступен worker»;
- README, диаграмма, реальные результаты load test и видео-демо на 5–7 минут.

Критерии готовности: повторный запрос не создаёт вторую операцию; рестарт worker не теряет событие; повторный webhook ничего не применяет дважды; временная ошибка вызывает retry, постоянная — DLQ; один trace связывает API, outbox и worker; чистый checkout поднимается по README. **Feature freeze — день 19.**

Не строить большой продукт. Цель — за 10 дней создать компактное доказательство senior-навыков и материал для system design-интервью.

## 6. Ежедневный режим

## 8. Воронка и критерии управления

Вести таблицу:

`Дата | Компания | Роль | Вилка gross/net | Ссылка | Fit 1–5 | Отклик | HR | Tech | Final | Отказ/причина | Follow-up`

### Целевые показатели за месяц

- 70–80 адресных откликов;
- 40–50 персонализированных сообщений бывшим коллегам, рекрутерам и нанимающим руководителям;
- 10+ HR-скринингов;
- 5+ технических интервью;
- 2+ финальных этапа;
- 1 письменный оффер от 300 000 ₽ net.

### Правила коррекции

- меньше 10% приглашений после 30 откликов → проблема резюме/позиционирования;
- HR проходит, но меньше 40% переходов на tech → проблема карьерной истории, зарплатных ожиданий или fit;
- меньше 50% переходов после tech → разбирать конкретные вопросы и дополнять проект;
- финалы без оффера → усиливать behavioral, ownership, references и переговоры;
- не считать массовость успехом: 4 точных отклика лучше 20 нерелевантных.

Считать конверсии только по откликам старше пяти рабочих дней: `response rate = содержательные ответы / отклики`, `HR conversion = HR / содержательные ответы`, `technical conversion = tech / завершённые HR`, `final conversion = final / завершённые tech`. Ориентиры: response rate ≥15%, HR→tech ≥50–60%, tech→final ≥40%. При response rate <10% после 20 созревших откликов менять верхнюю треть резюме, выбор вакансий или канал, а не покупать очередной курс.
